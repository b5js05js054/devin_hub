[白岚]

## 结论

**`subapi2` 快，主要是原生 SSE 路径短、逐事件立即下发；你的 `server-go` 其实也做到了及时 `Flush`，慢点主要发生在“上游尚未产生有效内容”以及重试、停滞阶段，不是 Go 写出流太慢。**

现有抓包也支持这个判断：在 `server-go/20261029_NsWsh` 的 **289 条可解析记录**中：

| 指标 | 中位数 | P90 | 最大值 |
|---|---:|---:|---:|
| 首个有效正文/思考/工具内容 | 8.60 秒 | 18.82 秒 | 124.96 秒 |
| 相邻有效输出最大间隔 | 0.96 秒 | 5.24 秒 | 38.73 秒 |

所以你的“有时候很慢”包含两类问题：

1. **首字等待很长**：主要是模型/渠道生成慢、连接建立或重试对冲。
2. **已经开始输出后又停住**：第三方渠道流不稳定。

> 这些计时从中继完成请求转换、准备发起第三方请求后开始，不包含前面的卡密、计费预检和排队时间，因此不是完整端到端 TTFT。

## 为什么 `subapi2` 显得快

### 1. 原生 Chat Completions 可以近似透明转发

当账号使用原生 Chat Completions 协议时：

`ForwardAsChatCompletions`  
→ `forwardAsRawChatCompletions`  
→ `streamRawChatCompletions`

见：

- `subapi2/backend/internal/service/openai_gateway_chat_completions.go:140`
- `subapi2/backend/internal/service/openai_gateway_chat_completions_raw.go:39`
- `subapi2/backend/internal/service/openai_gateway_chat_completions_raw.go:300`

这条路径主要是：

- 改写模型名；
- 补充 `stream_options.include_usage`；
- 逐行读取上游 SSE；
- 必要时替换模型名；
- 写出并 `Flush`。

关键写出循环在 `openai_gateway_chat_completions_raw.go:360-392`，没有等完整回答，也没有固定时间聚合缓冲。

即使走 Anthropic 转换路径，也是每个事件转换后立即 `Flush`：

- `gateway_forward_as_chat_completions.go:464-475`

**但这不是所有账号都走同一条路径。** Responses、Anthropic、OAuth 等账号仍会做协议转换，不能笼统说 `subapi2` 完全没有转换成本。

### 2. 它没有你这条 Devin 第三方接管的完整处理链

你的第三方链路是：

`Devin Connect/protobuf`  
→ 解析并重建 OpenAI/Anthropic 请求  
→ 渠道选择  
→ SSE 解析  
→ 思考标签拆分  
→ 工具调用纠偏  
→ Devin protobuf/Connect 帧重建  
→ 客户端

此外还有：

- 首字前故障切换；
- 对冲请求；
- 瞬时错误重试；
- 断流自动续答；
- 工具参数分段限速；
- 卡密和余额预检。

这些功能提高兼容性，但也增加了首字前后的等待点和故障恢复时间。

## 你的 `server-go` 不是忘了 Flush

第三方路径会先返回响应头：

- `server-go/internal/relay/thirdparty.go:1195-1210`

之后每个正文、思考、工具增量都会立即写出并 `Flush`：

- `thirdparty.go:1226-1248`
- `thirdparty.go:1359-1403`

官方透传路径也是每块写出后立即刷新：

- `server-go/internal/relay/server.go:1078-1100`

`bufio.Reader` 在这里只是按行解析 SSE，不代表会缓冲到 64KB 才向下游发送。

**因此，单纯照搬 `subapi2` 的 Flush 代码，基本不会解决你现在的几十秒等待。**

## 慢点按优先级排序

### 1. 第三方上游首字慢，是当前证据最充分的主因

第三方路径会暂扣响应头、消息 ID、usage 等非内容事件，直到收到真正的正文、思考或工具调用：

- `thirdparty.go:1595-1640`

这是为了避免把保活帧误认为模型已经开始回答。

所以当前现象通常是：

- HTTP 已连接；
- 中继每 1.5 秒发送空心跳；
- 但模型迟迟没有有效内容；
- 客户端看起来就像“卡住”。

这不是中继已经拿到正文却没发，而是**有效正文尚未到达**。

现有记录中最慢的一条首内容约 125 秒，并且对应多段上游请求，说明异常等待和恢复机制也参与其中；具体是对冲还是重试，需要对应 `relay.log` 才能区分。

### 2. 重试、对冲和自动续答会放大异常请求的耗时

当前未显式配置相关参数，因此使用代码默认值：

- 首字停滞窗口：120 秒；
- 出字后停滞窗口：60 秒；
- 每 30 秒补发一路对冲请求；
- 最多补发两路。

见 `thirdparty.go:49-62`。

此外还有：

- 首包前最多两次瞬时错误重试：`thirdparty.go:1825-1842`；
- 首内容前渠道切换：`thirdparty.go:1598-1669`；
- 断流后的自动续答：`thirdparty.go:1844-1874`。

它们能够救回异常请求，但一次请求可能因此经历多轮连接和生成，不能完全消除长尾延迟。

### 3. 流中停顿也确实存在

抓包中有效输出最大间隔 P90 约 5.24 秒，最大约 38.73 秒。

对应代码已经识别并处理这种情况：

- 出字后长期没有有效内容，判定停滞；
- 尝试自动续答或切换渠道。

所以“偶尔慢”不只是首字问题，**渠道中途停流也是实际存在的现象**。

### 4. 工具参数有人为限速，但只影响工具调用阶段

实际配置为：

- 每片 200 字节；
- 片间 15ms；
- 单个工具调用节奏总时长最多约 2 秒。

见：

- `server-go/config.json:73-74`
- `server-go/internal/relay/tool_pace.go:13-17`

它会让大段工具参数看起来逐字输出，但：

- 不影响普通正文首字；
- 单个调用最多约 2 秒；
- 无法解释几十秒的首字等待。

因此它不是当前主因。

### 5. 卡密后台的同步预检是独立候选延迟点

收费模型或倍率未知的第三方模型会先请求：

`server-go`  
→ `card-auth-system /api/billing/relay/precheck`  
→ SQLite 查询和余额判断  
→ 才进入排队与上游请求

见：

- `server-go/internal/relay/server.go:756-773`
- `server-go/internal/billing/billing.go:128-135`
- `server-go/internal/relay/billing.go:35-60`

该 HTTP 客户端超时为 8 秒，后台异常时确实可能增加等待；但失败后通常会直接拒绝，不会表现为持续几十秒的正常流式响应。

免费模型会直接放行，结算则是异步的，不阻塞流式输出。

**目前没有预检耗时日志，不能把卡密后台定为根因。** 特别是 `handleRelay` 的 `reqStart` 在预检之后才设置，所以现有 `text.txt` 分段耗时天然看不到这一阶段。

## 最终判断

| 项目 | 判断 |
|---|---|
| `subapi2` 的流式写出 | 原生路径短，逐行/逐事件 Flush，是其流畅的重要原因 |
| `server-go` 是否缺少 Flush | **不是，已经及时 Flush** |
| 首字偶尔几十秒 | **当前证据主要指向第三方上游、连接/生成等待及恢复机制** |
| 流中偶尔停住 | **有抓包证据，最大有效输出间隔约 38.7 秒** |
| 工具参数限速 | 有少量人为延迟，但不是首字慢主因 |
| `card-auth-system` | 预检可能增加前置耗时，但目前没有证据认定为主因 |
| 并发排队 | 实际配置为 64，仍需运行日志才能判断是否打满 |

**下一步最应该补的是计时，而不是先改流式写出：**分别记录预检、排队、上游连接、响应头、首个有效 delta、首次下游写出和各次重试耗时，并用相同模型、相同请求、相同上游对比 `subapi2`。否则拿两个不同渠道的首字速度直接比较，会把模型和渠道差异误算成代码差异。

本次仅进行了只读代码和抓包分析，没有修改文件或运行基准测试。
